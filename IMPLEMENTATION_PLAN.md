# iPhone App Transfer — план MVP и поставки

Этот документ — исполняемое задание, а не предложение заново выбрать продукт. Концепция и дизайн утверждены. Читать вместе с `PRODUCT.md`, `DESIGN.md`, `docs/ARCHITECTURE.md` и `research/FINDINGS.md`.

**Результат:** рабочий SwiftUI `.app` и DMG для Apple Silicon/macOS 15+, работающие без установленного iMazing, Homebrew и внешнего ipatool; реальные USB-операции и GUI-авторизация; библиотека с удалением, очередь, журнал, настройки и утверждённый дизайн.


## Текущий этап: переименование и приватная поставка

MVP уже существует. Этапы 0–12 ниже сохраняют исходный план и критерии, а не требуют повторной реализации. Сначала прочитать `STATUS.md` и `docs/QA.md` и сверить фактическое состояние Git/GitHub. Пользователь одобрил эту последовательность 19.10.2026:

1. Обновить видимый бренд на **iPhone App Transfer** в UI, bundle, DMG и текущих документах. Сохранить Bundle ID, Keychain, UserDefaults, пути библиотеки/кэша и внутренние Swift-модули ради совместимости.
2. Выпустить 0.1.4 (5): `dist/iPhone App Transfer.app` и `dist/iPhone-App-Transfer-0.1.4-arm64.dmg` с SHA-256. Старые артефакты и их evidence не переименовывать.
3. Довести RU/EN README, ссылки, приватность и инструкции GitHub CLI; исключить реальные IPA, аккаунты, дампы, секреты и private-логи из первого коммита.
4. Пройти локальные проверки и packaging, сохранить результат в STATUS/QA. Отдельно оставить pending live-проверки второго телефона/аккаунта и чистого Mac.
5. Создать первый source commit в `main`, приватный `Daveedick/iphone-app-transfer`, отправить исходники и проверить remote SHA/PRIVATE.
6. Создать приватный prerelease `v0.1.4`, добавить DMG/checksum, проверить скачивание и свежий clone. Команды и проверки: `docs/GITHUB_SETUP.md`.
7. Сохранить репозиторий приватным. Переход в public требует последующего решения пользователя, выбора лицензии собственного кода и завершения необходимых проверок.

Текущая авторизация включает commit/push/private release; прежние запреты ниже относились к исходному этапу локальной реализации. Они не отменяют одобренную приватную поставку. Реальные установки/удаления на телефонах и изменение глобального Gatekeeper в эту поставку не входят.

## Исходный план реализации: порядок и контрольные точки

Ранние этапы закрывают технические риски до большой полировки UI. Каждый этап заканчивается артефактом и проверкой. Не выдавать mock-preview за завершение продуктового этапа. Не добавлять сервер, переписывание App Store-протокола, синхронизацию банковских сессий или дополнительные платформы.

### 0. Прочитать пакет и проверить среду

1. Открыть approved prototype в браузере и посмотреть обе темы/плотности/настройки/очередь.
2. Проверить текущие `swift --version`, developer directory, macOS, Go и доступность SDK. Исследование обнаружило CLT Swift 6.0.3 и невыбранный full Xcode — проверить актуальное состояние, не считать это уже исправленным.
3. Создать выбранную минимальную структуру SwiftPM + Go helper + scripts. Не поднимать remote и не пушить.
4. Дополнить `.gitignore`, чтобы runtime state, IPA, private phone dumps и credentials не попадали в код.
5. В `STATUS.md` записать фактические версии и ограничения. Согласованные решения не переспрашивать.

**Готово:** минимальное пустое native окно запускается локально, понятны команды сборки и целевая macOS; UI ещё не объявлен готовым.

### 1. Воспроизводимые зависимости и минимальный bundle

1. Зафиксировать источники/версии/checksums libimobiledevice, libplist и transitive dependencies; определить license notices.
2. Зафиксировать upstream ipatool revision. Проверенный ориентир — release 2.7.0; не использовать непроверенный `main` только потому, что он лежит в Downloads.
3. Проверить, что импорт его core собирается отдельно; обработать required Go version, локальные module replacements, SAP assets и runtime cache.
4. Собрать arm64 `.app` с stub helper и библиотеками внутри bundle. Задать bundle ID, версию, deployment target, provisional icon/resource layout.
5. Проверить зависимости и запуск без поиска runtime в Homebrew. Пока не тратить время на DMG-фон, polish и auto-update.

**Готово:** app и stub helper стартуют из `.app`; нет runtime-ссылок на рабочие каталоги. Список зависимостей и лицензий записан.

### 2. Нативное чтение телефонов без iMazing

1. Перенести идею `research/evidence/device_metadata_probe.c` в тонкий C-мост и Swift DeviceService; не использовать CLI как production backend.
2. Реализовать initial USB enumeration, hotplug и независимое состояние каждого устройства.
3. Показать реальные имя/модель/iOS, locked/trust/disconnected; pairing инициировать только в понятном connect-flow.
4. Прочитать список через Lookup с `ShowPlaceholders=true` и явным `iTunesMetadata`. Разобрать store ID, external version ID, account hint, offloaded/TestFlight признаки.
5. Обработать неполные/битые plist и получить иконки с fallback; ни одна строка не должна ломать весь список.
6. Проверить реальный доступный телефон. При доступности iOS 27 выполнить отдельную проверку: ранее direct-metadata experiment подтверждён только на iOS 18.5.

**Готово:** в приложении виден настоящий список без iMazing/CSV; reconnect и несколько устройств не смешивают данные. Для отсутствующего iOS/устройства статус проверки честно записан как pending.

### 3. GUI Apple Account + helper contract

1. Реализовать JSON-lines IPC с request IDs, событиями и protocol version. Написать небольшой adapter к ipatool core.
2. Реализовать native формы email/пароль и 2FA: preparing → credentials → code-required → success/ошибка. Пользователь вводит секреты непосредственно в GUI.
3. Пароли/OTP не передавать в argv/env и не логировать. Keychain/cookies изолировать от существующего ipatool и между аккаунтами.
4. Проверить истечение сессии, отмену ввода, неверный код, сетевую ошибку, helper crash и повторное открытие UI после потери фокуса.
5. Войти с чистым app namespace и сделать один реальный запрос version metadata. Это важнее декоративного полноэкранного UI.
6. Проверить два аккаунта: переключение не подменяет cookies, owner IPA или историю. Если доступен только один, проверить изоляцию синтетическим контрактным тестом и отметить второй live-login pending.

**Готово:** реальный GUI login/2FA и App Store request без Terminal, без старых сессий и секретов в логах. Не продолжать презентацию «полностью работающего MVP», если этот риск не закрыт.

### 4. Локальная библиотека и скачивание

1. Реализовать `LibraryItem`, атомарный versioned manifest, managed storage и `.partial` lifecycle.
2. По live metadata скачать exact source version; альтернативную предложить только после явного выбора пользователя.
3. Привязать каждый IPA к версии/build/owner-account, посчитать hash и проверить архив по архитектурному контракту.
4. После успеха показать запись в библиотеке. После сбоя не показывать `.partial` как готовый IPA.
5. Реализовать повторное использование подходящего архива, missing-file recovery и сохранность после перезапуска.
6. Лицензия недоступна/аккаунт неизвестен/TestFlight — понятная ошибка/неподдерживаемое состояние. Не пытаться автоматически купить платное приложение. Получение бесплатной лицензии, если понадобится, должно быть явно обозначенным действием.

**Готово:** приложение из реального списка скачано через GUI в собственную библиотеку и переживает перезапуск. Download-only не меняет телефоны.

### 5. Первый полный перенос на конкретный телефон

1. Реализовать AFC staging + installation_proxy install через C-мост, callbacks и cleanup.
2. Использовать явно определённый UDID, проверить target iOS/free space/installed bundle before action.
3. Установить одно подходящее тестовое приложение на разрешённое пользователем устройство; не использовать существующий банковский app как расходный тест.
4. После завершения перечитать bundle ID/version с того же телефона. Не удалять placeholder/app для «починки» неудачной установки.
5. Отдельно попросить пользователя подтвердить запуск и обработать возможный Apple Account prompt. Установка и запуск — разные доказательства.

**Готово:** сквозной реальный путь «прочитали метаданные → скачали → проверили → установили → перечитали состояние». Путь должен работать из bundled app, а не только из разработческого терминала.

### 6. Очередь и устойчивость

1. Один TransferCoordinator с последовательным исполнением и immutable target/account/version references.
2. Поддержать download-only, transfer, install-library-item; batch selection создаёт отдельные задачи.
3. Реализовать stage progress, waiting-for-device/account/version-choice, skip existing, ошибки и bounded retries.
4. Pause/cancel делать на поддерживаемых безопасных границах. Не убивать установку посередине ради мгновенной смены надписи.
5. Сохранять задачи/результаты. После app/helper crash или USB disconnect сначала сверять фактическое состояние, затем предлагать retry.
6. Сворачивание очереди не влияет на worker. Неуспех одной задачи не отменяет остальные независимые.

**Готово:** несколько приложений идут последовательно; disconnect не меняет target; crash не даёт ложного успеха и дублирования установки. Тесты проверяют эти инварианты, а не повторяют строки реализации.

### 7. Утверждённый интерфейс на настоящих сервисах

1. Построить native shell: общая library sidebar, horizontal device workspace, queue, activity, accounts и settings.
2. Подключить реальные services/view models; demo data оставлять только в previews/явном demo mode.
3. Реализовать 0/1/3/5+ device states, independent search, single/multi-selection, быстрый переход к колонке.
4. Реализовать три направления drag-and-drop, допустимые/недопустимые drop targets, badge количества и drag-edge scrolling.
5. Добавить button/context-menu equivalent. Для множества destinations использовать меню, не бесконечную полосу кнопок.
6. Согласовать размеры и плотность с approved screenshot. Материалы, иконки и фон нативные; не копировать mock desktop frame или упрощённые банковские логотипы.

**Готово:** три реальных/контролируемых device models отображаются как в концепции, все основные действия доступны мышью и клавиатурой; число подключённых телефонов не ограничено константой 2/3.

### 8. Обязательное удаление из библиотеки

1. Контекстное меню и action bar «Удалить из библиотеки…», single/batch confirmation с количеством/версией.
2. Отдельная проверка queued/active references; busy-файл не удаляется.
3. Перемещение IPA в Trash, затем manifest update. Обработать partial failure, отсутствующий файл, перезапуск посреди операции.
4. Сохранённые на телефонах приложения и авторизации остаются нетронутыми. Действие нельзя перепутать с device uninstall.

**Готово:** пользователь понимает, где удалять сохранённые архивы; файлы действительно уходят в Корзину, список/объём актуальны, очередь и телефоны не повреждены.

### 9. Настройки, журнал, popover и доступность

1. RU/EN для всего интерфейса, действий, ошибок, singular/plural и accessibility labels; переключение без перезапуска.
2. Compact default / comfortable, system/light/dark; persistent preferences, sidebar/queue/window state.
3. Account/settings popover закрываются на outside click, app deactivation и Escape; смена popover закрывает предыдущий. Уточнить focus return и исключения для system panels/auth.
4. Журнал содержит действия и аккаунт, но не секреты. Сохранить meaningful failure stage и возможность повторить разрешённую операцию.
5. Нативные короткие press/selection/sidebar/drop feedback transitions, без perpetual animation. Уважать Reduce Motion/Transparency и Increase Contrast.
6. Проверить светлую и тёмную темы, обе локали, узкое окно, длинные названия, большой список, Tab/VoiceOver labels.

**Готово:** последние поправки пользователя реализованы; overlay нельзя оставить висеть поверх другого приложения; настройки сохраняются и не меняют реальные операции.

### 10. Опциональные дополнения P1

Выполнять только после работоспособного обязательного пути; не задерживать MVP из-за этих пунктов.

- Импорт собственного IPA: file picker → copy into managed storage → validate → owner/compatibility state. Не удалять original import source.
- Удаление с телефона: отдельная явная функция через `instproxy_uninstall`, подтверждение данных/устройства, readback и журнал. Только тестовое приложение, на удаление которого есть разрешение. Если безопасная проверка не выполнена, функцию скрыть/оставить за feature flag и честно отметить deferred.

### 11. Релизная сборка и DMG

1. Build scripts собирают `.app` и embedded helper/dependencies из pinned источников. Записать developer prerequisites, не перекладывая их на конечного пользователя.
2. Проверить arm64/minimum OS/`otool -L`/rpaths каждого Mach-O. Все third-party runtimes находятся в bundle или документированном первом запуске, без привязки к кэшу автора.
3. Добавить реальные app icon, version, bundle metadata, licenses/notices. Не выбирать лицензию проекта случайно из шаблона: предложенный default для собственного кода MIT, проверить совместимость состава до публикации.
4. Ad-hoc signing всех частей и verification. Собрать DMG с приложением и ссылкой Applications, понятной раскладкой и короткой инструкцией.
5. Проверить запуск в новом пользовательском профиле / на другом Mac без Homebrew, iMazing, `~/.ipatool`, credentials и cached SAP assets. Одно изменение PATH не доказывает чистую среду.
6. Проверить реальный downloaded/quarantined artifact, Gatekeeper-flow и запуск after move to Applications. Не требовать `sudo spctl --global-disable`.
7. Не требовать Apple Developer Program. Не называть ad-hoc подпись нотариализацией.

**Готово:** перенос выполняется из релизного bundle в чистой среде, пользователь не вводит команды в Terminal. Если второго Mac/нужной macOS нет, выпустить только проверенный preview с явным списком непроверенного, не называть его полностью проверенным релизом.

### 12. Приёмка и передача

1. Пройти `docs/ACCEPTANCE.md`; каждую live-проверку подкрепить кратким результатом, версией OS и артефактом, без приватных дампов.
2. Сохранить screenshots главных состояний и summary тестов. Отделить mock, local native, live device и clean-user проверки.
3. Обновить README: установка, первый login/2FA/trust, ограничения переноса, библиотека/удаление, обход только допустимого Gatekeeper-предупреждения, known issues.
4. Обновить STATUS, список зависимостей и инструкции воспроизводимой сборки.
5. Передать пути к `.app` и `.dmg`, checksums и оставшиеся ограничения. Commit/push/GitHub release выполняются только при отдельном указании пользователя.

**Готово:** пользователь получает конкретный устанавливаемый результат с проверками, а не демонстрацию с подставными успехами.

## Работа при внешних блокерах

- Нет подключённого/разблокированного телефона: показать точную причину, запросить действие и продолжить UI/domain/packaging, не симулировать live успех.
- Нужны пароль/2FA: ввод только в GUI пользователя; не спрашивать секреты в чате.
- Нет второго аккаунта/второго Mac/iOS 27: пометить соответствующую live-проверку pending, продолжить всё независимое.
- Apple временно не выдаёт IPA: сохранить typed error, не переписывать протокол вслепую и не менять версии/аккаунт без ведома пользователя.
- Требуется новая зависимость/SDK: обосновать необходимость фактом, не начинать массовое обновление Mac.

## Приоритет

**P0:** чтение телефонов → GUI auth → verified download → verified install → очередь → многоколонный UI → библиотека с удалением → настройки/popover/журнал → самостоятельный DMG.

**P1:** импорт IPA и безопасный device uninstall. Они не заменяют ни один незакрытый P0.
